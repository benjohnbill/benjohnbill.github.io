clangd · -std=gnu23 -Wall03 / 06

무엇이 문제였을까? - Type Casting

생각해 보니 처음엔 빨간 밑줄이 있었던 것 같기도…

first_fit() 의 조건에디터 (clangd)
GET_SIZE(bp) >= bsizeOrdered comparison between pointer and integer ('unsigned int' and 'unsigned int (*)(size_t)')
GET_SIZE(bp) >= (size_t)bsize진단 없음 (gcc -Wall도 0개)

Casting을 붙이면, 컴파일러는 개발자의 의도라고 믿는다.

mm.c타입
#define GET_SIZE(bp)  ((unsigned int)(...))
static unsigned int bsize(size_t psize)

그러나.. 애초에 둘 다 unsigned int였다. 애초에 내 실수..

(size_t)bsize = 함수 주소를 정수로

▸1생각해 보니 처음엔 빨간 밑줄이 있었던 것 같기도 해요.

▸2캐스트 없이 쓰면 에디터가 포인터와 정수를 비교한다고 경고해요. 캐스트를 붙이면 아무 말도 안 해요.

▸3아, 캐스팅해 버리니까 그냥 경고를 지워 버렸구나. 제가 size_t로 캐스팅하니까 컴파일러는 개발자의 의도라고 알았나 봐요.

▸4그리고 생각해 보니 GET_SIZE부터가 unsigned int라서, 캐스팅 자체가 애초에 잘못이었어요. (5초)

퀴즈 · bsize()04 / 06

unsigned int 타입의 bsize(4GB + 16)은 몇일까?

mm.c · bsize()?
static unsigned int bsize(size_t psize){
    return HSIZE + (unsigned int)exact_psize(psize) + FSIZE;
}
상수
HSIZE = FSIZE = 4
DSIZE = 8

UINT_MAX = 2³² − 1   // 약 4GB
bsize()

여기서 퀴즈 하나 낼게요. 이 상태에서 bsize에 4GB 더하기 16을 넣으면 몇이 나올까요? size_t로 받아서 unsigned int로 돌려준다는 점을 잘 보세요.

(3초쯤 기다린다)

답 · bsize(4294967312)05 / 06

unsigned int는 4GB가 넘는 정보를 잘라낸다

gcc -Wall -Wextra -Wconversion · 0 warnings실제 기록
request      = 4294967312
bsize(req)   = 24

4GB + 24가 아니라 24

mm.c · mm_malloc()가드
void *mm_malloc(size_t size){
    if (size == 0 || size >= MAX_HEAP){   // MAX_HEAP = 20MB        return NULL;
    }

물론, 우리 malloc()은 20MB 가드가 먼저 막는다.

mm.c · exact_psize() · 제안주석
/* MAX_HEAP(20MB) 가드가 있어서 4GB를 넘는 크기는 여기 오지 않는다.
   가드가 없다면 이 캐스트는 크기를 잘라 낸다. */
return (unsigned int)psize;

그래도 왜 괜찮은지 주석으로 남겨 두는 게 좋지 않을까?

24는 bsize()의 값 · malloc(4GB+16)은 가드에서 NULL

▸1답은 24예요. 4GB + 24가 아니라 24. exact_psize() 안의 (unsigned int) 캐스트가 앞자리를 잘라 냈어요.

▸2그런데 실제 malloc은 여기까지 오지도 않아요. mm_malloc 맨 앞에서 20MB 가드가 먼저 NULL을 돌려줘요. 그래서 저희 코드에선 이 캐스트가 문제가 안 돼요. 저도 실제로 그렇게 짜 뒀어요.

▸3다만 캐스트를 쓴다면, 왜 괜찮은지 주석으로 남겨 두는 게 맞다고 생각해요.

(질문이 오면) 캐스트를 빼면 -Wconversion이 "conversion from 'size_t' to 'unsigned int' may change value"라고 알려 줘요. 캐스트를 붙이면 조용해져요. -Wall만으로는 둘 다 조용해요.
