fault 난 주소에서 struct page까지

SPT · hash · page 세 구조체의 연결. 갈림길은 page 안의 spt_elem 한 줄

필드 순서 = week09 include/vm/vm.h · hash 값 = lab/spt-probe 실행 결과 · 청록 = SPT가 엮는 고리 · 빨강 점선 = Hunk 1 이전에 없던 것

1. 누가 무엇을 가리키나

thread → spt(struct hash) → buckets[] → 서랍 list → 힙의 page 안 spt_elem

SPT는 page를 담지 않음 → page는 힙에 따로 · 서랍 list가 page 안 spt_elem만 엮음. 0x401000 = claim 끝(frame·PML4 있음) · 0x400000 = frame = NULL, PML4에도 없음

2. spt_elem · pages가 없으면

청록 고리 전부 사라짐 → page는 힙에 그대로, thread에서 page로 가는 길 없음

0x400000 fault → 커널이 page를 못 찾음 · 종료 때 free할 목록도 없음. frame·PML4 쪽은 1번과 같음 → 두 줄의 일 = page로 가는 길

2-2. fork 직후: 부모 spt와 자식 spt

supplemental_page_table_copy() → 부모 page마다 자식 spt에 새 page · 새 frame. 같은 va · 같은 내용, 다른 주소

값 = fork-once 실행 중 __do_fork()에서 copy 직후 찍은 probe 출력 · 보라 = 부모와 자식의 값이 다른 칸

① 부모: fork()를 부른 thread

② 자식: __do_fork() 안, copy 직후

같음 = va · elem_cnt · bucket_cnt · 서랍 번호 · 로드된 page의 operations · 내용 바이트. 다름 = 구조체 주소와 그 주소를 담은 포인터 전부(spt_elem의 prev·next 포함) · 0x3ff000의 상태 · 서랍 안 순서

서랍 안 순서 반대 = hash_insert()가 list_push_front()로 넣음 → 부모 순회 순서대로 넣으면 뒤집힘

부모 pagecopy()가 자식 쪽에서 부르는 것내용 출처
UNINIT (0x3ff000)vm_alloc_page_with_initializer(type, va, writable, init, aux 사본) → vm_claim_page(va)파일: load_info의 file · ofs · read_bytes
ANON, 로드됨 (나머지 8개)vm_alloc_page(VM_ANON, va, writable) → vm_claim_page(va) → memcpy부모 frame->kva 4KB

vm_alloc_page_with_initializer() = page malloc · page_initializer 고르기 · uninit_new() · spt 삽입. frame · PML4 · 내용 없음, aux는 받은 포인터 그대로 보관

vm_claim_page() = 자식 spt에서 va로 page 찾기 → page·frame 연결 · PML4 매핑 → swap_in() → uninit_initialize()가 page_initializer, 이어서 init(page, aux) 실행 = 내용 채우기

aux 사본 이유 = page 하나에 load_info 하나, free 한 번(lazy_load_segment() 또는 uninit_destroy()). 포인터 공유 → 자식 claim이 free → 부모 page에 해제된 주소 → 부모 fault 때 use-after-free, 종료 때 double free

3. fault 주소에서 page 찾기

내리기 → 해시 → 서랍 고르기 → 비교 → hash_entry. PML4는 보지 않음

내리기 생략 → 키 0x401234는 어느 서랍에도 없음 → NULL (make run EXTRA=-DNO_ROUND). probe의 page에는 operations가 없어서 24 대신 16

7. 찾은 page에 frame 붙이기: page·frame과 두 연결은 언제 생기고 언제 사라지나

page(va)는 SPT 등록부터 프로세스 종료까지 살아 있음 · frame(kva)은 claim 때 생김 · 둘을 잇는 연결은 두 가지 = 소프트웨어 기록(page->frame ⇄ frame->page)과 하드웨어 번역(PTE) · 연결은 eviction 때 끊기고, 두 구조체는 그 뒤에도 남음

세로 = 호출 순서 · 바깥 굵은 막대 = 구조체가 살아 있는 구간 · 안쪽 가는 막대와 음영 = 연결이 살아 있는 구간 · ● 생김 · ✕ 사라짐 · 점선 = 아직 안 짠 단계 · 빨강 점선 = 틀린 버전

그림 2 = pml4_set_page()가 false일 때. 여기까지 생긴 것 = frame(kva)과 연결 ① · 연결 ②(PTE)는 없음 · 두 버전의 차이는 frame 막대가 어디서 끝나느냐 하나뿐

false가 나는 곳 = pml4e_walk()의 세 단계(pdp · pd · pt 표) 중 한 곳에서 palloc_get_page(PAL_ZERO) 실패 · PAL_USER 없음 → kernel pool 쪽 고갈 · 그 호출에서 새로 단 중간 표는 walk가 스스로 반납(allocated) → vm_do_claim_page()도 자기가 만든 것(frame · 연결)을 자기가 치움

8. mmap: 파일 바이트가 va에 보이기까지

파일 내용은 디스크에만 있음 → 커널 힙의 struct file은 위치표, 사용자는 fd 번호만 가짐. mmap 호출 때는 아무것도 읽지 않음 → 그 va 첫 접근 때 page에 적어 둔 file · ofs로 읽어 옴

보라 = 파일 내용 바이트 · 청록 = mmap이 page에 적어 둔 약속 · 회색 점선 = 아직 코드에 없는 것

세 장소: 디스크 · 커널 메모리 · 사용자 va

struct file = 내용이 아니라 "어느 inode의 몇 번째 바이트부터"를 적은 16바이트 표 · pos = 다음 file_read()가 읽을 위치 · struct inode = 파일마다 하나, open_cnt로 몇 개의 file이 보는지 셈. 사용자가 fd를 close해도 매핑은 남아야 함 → mmap 몫 사본이 따로 필요

addr와 offset: 서로 다른 좌표

offset = PGSIZE 배수 → 파일 page 경계와 va page 경계가 맞음 · do_mmap()의 검사 = pg_ofs(offset) != 0 → NULL. addr는 파일 위치가 아님: B에서 0x10000000에 보이는 것 = 파일 4096번 바이트

read와 zero 계산

/* 총량: mmap 한 번에 */
read = min(length, file_length − offset)     /* 파일에서 가져올 바이트 */
zero = ROUND_UP(length, PGSIZE) − read        /* 0으로 채울 바이트 */

/* load_segment() 루프: page 하나마다 */
page_read_bytes = read_bytes < PGSIZE ? read_bytes : PGSIZE;
page_zero_bytes = PGSIZE − page_read_bytes;
read_bytes -= page_read_bytes;   zero_bytes -= page_zero_bytes;
upage      += PGSIZE;            ofs        += page_read_bytes;
