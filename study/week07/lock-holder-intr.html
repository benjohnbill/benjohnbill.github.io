intr_context () · 지금 외부 인터럽트 핸들러 안에서 실행 중인지 알려 주는 함수. 핸들러 안이면 true

인터럽트 핸들러는 잠들 수 없다. 따라서 잠들 수 있는 lock은 핸들러에서 잡을 수 없다.


pintos -- -q run alarm-single

타이머 핸들러 안에서 lock_acquire를 한 번 불러 봤습니다. 50틱째에요.

▸1바로 PANIC입니다. 첫 줄 ASSERT에 걸려요. 호출 경로 맨 아래가 kernel_thread인데, 핸들러가 끼어든 스레드의 스택을 빌려 쓰고 있다는 뜻입니다.

▸2핸들러는 잠들 수 없어서 lock을 잡을 수 없습니다. 오늘 할 이야기는 이 한 줄이에요.

in_external_intr · intr_context ()가 읽는 표시. 핸들러에 들어갈 때 켜고, 핸들러가 돌아와야 끈다

핸들러가 잠든 tick 50이 이 커널의 마지막 틱이 됐다.


pintos -- -q -mlfqs run mlfqs-load-1

ASSERT를 빼면 어떻게 될까요. sema_down과 thread_block의 가드를 빼고 핸들러를 진짜로 재웠습니다. lock_acquire가 잠드는 곳이 바로 이 sema_down이에요.

▸1main이 핸들러 안에서 잠들고 idle이 이어서 달리는데, idle이 인터럽트를 켜려는 순간 또 ASSERT가 터집니다. 커널은 여전히 인터럽트 처리 중이라고 믿고 있어요.

▸2타이머 카운트도 50에서 멈췄습니다.

원인 · 핸들러가 돌아와야 끝나는 일

표시를 끄고 EOI를 보내는 코드는 핸들러가 돌아온 뒤에야 실행됨.

    in_external_intr = true;
   ⋮   생략
    handler = intr_handlers[frame->vec_no];
    if (handler != NULL)
        handler (frame);   ⋮   생략
    in_external_intr = false;

  • 345행에서 핸들러에 들어가며 표시를 켠다.
  • 352행의 핸들러가 잠들면 그 아래로 내려오지 못한다.
  • 369–370행의 표시 끄기와 EOI가 실행되지 않는다.

EOI · 인터럽트 컨트롤러(PIC)에 보내는 처리 끝 신호. 받기 전까지 같은 줄의 인터럽트를 다시 보내지 않는다

lock->holder는 스레드만 쓴다. 핸들러와 나누는 데이터는 lock이 아니라 인터럽트 끄기로 지킨다.

pintos/threads/interrupt.c · intr_handler2026-10 · WEEK 07

이유는 intr_handler에 있습니다.

▸1핸들러에 들어갈 때 "처리 중" 표시를 켜고

▸2핸들러가 돌아와야 표시를 끄고 PIC에 EOI를 보냅니다. 핸들러가 잠들면 이 두 줄까지 오지 못해요. 표시는 다음 스레드로 넘어가고, 타이머 인터럽트는 다시 오지 않습니다.

▸3그래서 lock->holder는 스레드만 씁니다. 핸들러와 같이 쓰는 데이터는 인터럽트를 꺼서 지킵니다.
