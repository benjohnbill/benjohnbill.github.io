exit(1)을 받아 줄 OS가 없을 때

같은 debug_panic, 내 코드 · Pintos user · Pintos kernel에서 끝이 다름. 갈림길은 밑에 받아 줄 OS의 유무

1. debug_panic()

내 코드(harness/boot.c)를 한 줄씩 읽다가 마지막 줄에서 멈춤. Pintos 커널의 같은 함수는 끝이 다름

/* 내 코드: harness/boot.c:42-43 */
printf ("\n");
exit (1);
/* lib/kernel/debug.c:41-43 */
if (power_off_when_done)
    power_off ();
for (;;);

커널은 왜 exit (1)로 끝나지 않을까?

2. 공통 코드

Pintos에는 두 벌: lib/user/debug.c (사용자 프로그램용) · lib/kernel/debug.c (커널용). 내 코드까지 셋 다 같은 다섯 줄:

printf ("Kernel PANIC at %s:%d in %s(): ", file, line, function);   // 어디서: 위치
va_start (args, message);
vprintf (message, args);                                             // 왜: 사유
va_end (args);
printf ("\n");

user는 첫 단어만 User process ABORT. kernel·user는 printf ("\n")과 va_end 순서가 반대

  • va_list args아직 안 읽은 가변 인자(...)를 가리키는 책갈피
  • va_start (args, message)책갈피를 message 다음, 첫 가변 인자에 꽂음
  • vprintf (message, args)... 대신 책갈피를 받는 printf
  • va_end (args)책갈피 정리, va_start와 짝

출력은 셋 다 세 조각. gdb로 write 시스템 콜을 잡으면 조각마다 한 번씩:

write #1  len=44  "Kernel PANIC at panic.c:21 in thread_foo(): "   ← printf
write #2  len=29  "assertion `t != NULL' failed."                  ← vprintf
write #3  len=1   "⏎"                                             ← printf
[Inferior 1 (process 32805) exited with code 01]                   ← exit(1)

3. 실제 코드: 뭐가 다를까?

공통 다섯 줄 뒤가 다름. 커널은 더하고, 내 코드의 exit(1)은 뺌. 굵은 줄은 공통 코드, 초록 줄은 내 코드에 없는 줄

// harness/boot.c:33-4433void34debug_panic (const char *file, int line, const char *function,35const char *message, ...) {36va_list args;3738printf ("Kernel PANIC at %s:%d in %s(): ", file, line, function);39va_start (args, message);40vprintf (message, args);41va_end (args);42printf ("\n");43exit (1);// 받는 쪽은 Linux44}
// lib/user/debug.c:9-249void10debug_panic (const char *file, int line, const char *function,11const char *message, ...) {12va_list args;1314printf ("User process ABORT at %s:%d in %s(): ", file, line, function);// 첫 단어만 다름1516va_start (args, message);17vprintf (message, args);18printf ("\n");19va_end (args);2021debug_backtrace ();// 호출 스택 출력2223exit (1);// 받는 쪽은 Pintos 커널 (시스템 콜)24}
// lib/kernel/debug.c:14-4414void15debug_panic (const char *file, int line, const char *function,16const char *message, ...) {17static int level;// 몇 번째 PANIC인가, 호출 사이에도 유지18va_list args;1920intr_disable ();// 타이머 인터럽트 끔: 죽는 중 다른 스레드로 안 넘어감21console_panic ();// 콘솔 락 무시: 락을 쥔 채 죽어도 출력2223level++;24if (level == 1) {// 첫 PANIC만 전체 출력25printf ("Kernel PANIC at %s:%d in %s(): ", file, line, function);2627va_start (args, message);28vprintf (message, args);29printf ("\n");30va_end (args);3132debug_backtrace ();// "Call stack: 0x…" 출력 (5절)33} else if (level == 2)// 출력하다 또 PANIC → 한 줄만34printf ("Kernel PANIC recursion at %s:%d in %s().\n",35file, line, function);36else {37/* Don't print anything: that's probably why we recursed. */38}3940serial_flush ();// 시리얼 버퍼에 남은 글자 밀어내기41if (power_off_when_done)42power_off ();// QEMU 끄기, 직전에 통계 출력43for (;;);// 못 끄면 영원히 멈춤44}

4. OS가 받아 줄 수 있냐의 차이

밑에 받아 줄 OS 있음 → exit(1) · 없음 → 스스로 꺼야 함

① 내 코드 (jingeunOS)

밑에 Linux 있음 → exit(1)만으로 정리 가능

② Pintos 사용자 프로그램

밑에 Pintos 커널 있음 → 그 프로세스만 정리, 커널은 계속 동작

③ Pintos 커널

받아 줄 OS 없음 → QEMU 전원 차단, 아니면 무한 대기

① 내 코드② user③ kernel
첫 단어Kernel PANICUser process ABORTKernel PANIC
공통 코드 (위치 + 사유 + ⏎)✓✓✓
backtrace—✓✓
인터럽트 끔 · 콘솔 락 무시 · 재귀 방지——✓
마지막exit(1) → Linuxexit(1) → Pintos 커널power_off() 또는 for(;;)
누가 받나LinuxPintos 커널아무도

5. 실물: Pintos와 Linux의 커널 PANIC

Linux 커널도 밑에 받아 줄 OS 없음 → 같은 순서, 같은 두 갈래: 끄거나(재시작) 무한 대기
