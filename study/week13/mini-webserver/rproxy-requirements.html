rproxy 요구분석: 단계마다 무엇을 보고 누구를 거르나

앞 단계일수록 서버 비용은 작지만 보이는 신호가 적음
뒤 단계일수록 신호는 많지만 그곳까지 오는 데 비용이 쌓임

주제요약
목표Observedcrawler의 요청은 cache miss로 Origin까지 가서 비용을 만들고, 돌려주는 방문자는 거의 없다.Meaning서버는 crawler를 가능한 한 앞 단계에서, 그 단계에 보이는 신호만으로 거른다.
사용자Observed운영자가 가르는 client는 셋이다: 진짜 사용자, 나쁜 crawler, 착한 bot.Meaning나쁜 crawler를 막는 일과 진짜 사용자를 잘못 막지 않는 일이 같은 무게를 갖는다.
단계별 검사Observedrproxy는 ClientHello 뒤의 Connection Verdict와 request parse 뒤의 Request Verdict, 두 번 판단한다.Meaningdrop은 TLS 서명 전에 끝나서 가장 싸고, 규칙 대부분은 신호가 많은 HTTP 단계에 몰린다.

이 노트는 mini-webserver CJG 브랜치의 SPEC, ADR, 코드, 측정 파일을 보고 썼다. 측정은 commit f9dda4d(Worker pool), 코드 위치는 commit a1e0984(Event loop) 기준이다. 출처 칩(primary)은 그 파일로 간다. 추론한 문장은 추론이라고 적었다.

1. 목표: 방어의 가성비

이득 없는 crawler 부하 → 요청이 단계를 지날수록 비용이 쌓임 → 앞 단계에서, 적은 신호로 거름

crawler의 요청은 사람이 잘 읽지 않는 드문 페이지를 긁어서 cache를 지나 Origin까지 간다. Read the Docs는 한 달에 73 TB, 5,000달러 넘게 썼고, AI crawler 3사가 돌려준 방문자는 요청 195 ~ 38,066번에 1명이었다 (01 비용).

그래서 이 노트는 rproxy를 운영자의 요구로 본다. 뒤 단계로 갈수록 거를 근거는 늘지만, 그곳까지 가려면 서버가 더 많이 주고받고 더 많이 쓴다. 가능한 한 적은 신호로, 앞 단계에서 걸러야 한다.

방어 하나가 남는 장사인지는 두 비교로 정한다.

비교어기면
방어 비용 < 그 방어가 아끼는 서빙 비용막는 편이 그냥 보내는 편보다 비싸다
방어 비용 < crawler가 그 방어를 피해 가는 비용군비 경쟁에서 서버가 먼저 지친다 (02 역사)

막을 대상만이 아니라 잘못 막으면 안 되는 대상도 요구

사용자운영자가 원하는 것잘못 판단하면Scene에서 보는 곳
진짜 사용자막지 않기. 느려지지 않기오탐: 사람이 막히거나 기다린다human.py의 200 수

착한 bot신원이 확인되면 통과시키거나 값을 받기검색 노출이나 거래를 잃는다signed의 200named의 402

3. 단계별 검사

단계 하나 = 카드 하나
카드마다 보이는 신호 → 거르는 기준 → 구분하는 사용자 → 서버 비용 → 고려할 점

Lesson과 따라치기도 이 카드 순서로 간다. 카드의 코드 칸이 따라칠 함수이고, Scene 칸이 Lesson의 예측 문제다.

5. Scene: Crawler script 10개

bench/arena/scene.sh <crawler> none layers는 Crawler script 하나와 human.py를 나란히, preset마다 10초씩 돌린다. Origin은 ./server --model pool --delay 10이다. Scene은 재기만 하고, 합격과 불합격을 가리지 않는다. primary

자세히: 두 preset의 flag

none: flag 없음. 그래도 robots.txt, Honeypot, User-Agent 규칙, scanner 규칙은 켜져 있다. 그래서 named, spread, signed는 none에서도 403을 받았고, trapped는 none에서도 drop됐다.

layers: 모든 방어를 켠다.

000은 응답이 없었다는 뜻이다. Origin이 보낸 MiB가 가장 크게 준 넷은 아래와 같다. 눈금은 로그다.

  • 10초에 약 59번 통과(repeat, longtail, revalidate, solver): token bucket이 처음에 10개를 주고, 그다음 초당 5개를 채운다. 10 + 5 × 10 = 60이다. rate limit의 열쇠는 IP이고, 이 넷은 IP 하나에서 보낸다.
  • repeat와 revalidate는 59번 통과했지만, Origin에 간 요청은 4번뿐이고 나머지 55번은 cache가 답했다. revalidate는 그 55번을 304로 받았다. 8.0 MiB는 2 MiB 파일 4번으로 보인다(추론).
  • signed는 named와 User-Agent(GPTBot/1.1)가 같다. 다른 것은 서명 하나이고, named는 402를, signed는 200을 받았다. Origin은 16.6 MiB를 보냈다. dataset이 16.7 MiB이고, 나머지 요청 2176개는 cache가 답했다.
  • spread의 주소 32개 중 Block list(127.0.0.16/28)에 든 16개는 handshake 전에 drop됐고(000), 나머지 16개는 402를 받았다.
  • trapped는 /trap/을 한 번 요청한 뒤 IP가 Block table에 들어갔고, 그 뒤 10초 동안 연결 6860개가 handshake 전에 drop됐다.

6. 대가와 한계

disguised는 Chrome User-Agent에 curl의 JA4를 보내므로, 요청마다 tarpit을 받는다. commit f9dda4d의 tarpit은 Worker 하나를 --tarpit 초(기본 10초) 동안 sleep으로 붙잡은 뒤 응답 없이 닫았다. Worker는 기본 4개였고 disguised는 loop 8개로 보냈다. Worker가 모두 묶이자 human.py는 대기열에서 10초를 기다렸고, 두 client 모두 응답을 하나도 받지 못했다. primary

1절의 첫 비교를 어긴 사례다: crawler를 붙잡는 방어가 서버의 자원도 붙잡아서, 진짜 사용자까지 멈췄다.

고침, 재측정 전 commit 617b815부터 rproxy는 CPU core마다 Event loop 하나로 돈다. tarpit은 이제 sleep이 아니라 timer다: socket은 열어 두고, 아무 thread도 기다리지 않는다(tarpit_start). 이 변경 뒤 Scene은 아직 다시 재지 않았다.

rproxy는 응답 하나를 보내고 연결을 닫으므로, 요청마다 TLS handshake를 한다. parity 측정에서 rproxy는 요청 하나에 CPU 2.1 ms를 썼고, 평문 HTTP와 keep-alive를 쓰던 Proxy Route는 0.08 ms를 썼다. 약 25배다. primary

계획, 아직 없음 rproxy의 keep-alive나 TLS session resumption이 있으면 handshake가 아니라 cache를 잴 수 있다고 측정 파일은 적었다. 아직 재지 않았다.

이 Scene의 한계:

  • curl로 만든 Crawler script는 모두 JA4 하나를 같이 쓴다. 그래서 Honeypot hit는 JA4가 아니라 IP만 Block table에 넣고, layers의 rate limit 열쇠도 IP다.
  • human.py는 Python urllib이고 TLS는 OpenSSL이다. 진짜 Chrome(BoringSSL)이 아니라 browser의 대역이고, JA4 table이 그 JA4를 browser라고 부를 뿐이다.
  • localhost에서 돌렸으므로, CIDR range 127.0.0.16/28이 hosting 회사의 ASN 목록을 대신한다.
  • rproxy에는 keep-alive가 없다. 연결 하나에 요청 하나이다.
  • 각 Scene은 preset마다 10초씩 한 번 돌린 값이다.
